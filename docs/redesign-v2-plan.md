# มีเกมก็แปล — แผนออกแบบและรื้อระบบ V2

วันที่: 23 ตุลาคม 2026

สถานะ: ข้อเสนอสำหรับการพัฒนาใหม่ อ้างอิงจากการตรวจโปรเจกต์ปัจจุบันและหน้า https://lusion.co/ ในวันที่จัดทำ แผนนี้ยังไม่ใช่งานที่พัฒนาหรือเผยแพร่แล้ว

## 1. เป้าหมายและทิศทาง

สร้างเว็บที่ให้ความรู้สึกเป็นสตูดิโอผู้สร้างงานแปลเกม มีหน้าแรกที่จดจำได้ และมีคลังม็อดที่เข้าถึงข้อมูลได้เร็ว

แนวคิดหลัก: **“ทุกโลก เล่นเป็นไทย” / Worlds, understood.**

นำหลักการจาก Lusion มาใช้ ได้แก่ พื้นที่ว่างมาก ลำดับตัวอักษรชัด ภาพหลักขนาดใหญ่ มุมโค้ง เมนูกระชับ และ motion ที่สัมพันธ์กับการเลื่อนหน้า ออกแบบภาพหลักและเอกลักษณ์สำหรับมีเกมก็แปลโดยเฉพาะ

หน้าแรกทำหน้าที่แนะนำแบรนด์และผลงาน ส่วนหน้าคลังและหน้ารายละเอียดเน้นค้นหา ตรวจเวอร์ชัน และดาวน์โหลด

ชื่อทิศทาง: **Playable Worlds**

| --- | --- |

| รูปทรง | พาเนลภาพใหญ่ มุมโค้งประมาณ 24–32px ปุ่มทรงแคปซูล |
| ภาพเกม | หนึ่งเกมเป็นจุดเด่นในแต่ละช่วง ใช้ภาพที่ความละเอียดเหมาะกับขนาดแสดง |
| โลโก้ | ใช้ต้นฉบับของเจ้าของและเก็บ provenance เดิม ทดสอบความชัดบนพื้นใหม่ |

ภาพหลักที่เสนอ: ฉากสามมิติของกรอบโลกเกมลอยอยู่รอบวงแหวนสีน้ำเงิน โดยมีชิ้นส่วนตัวอักษรไทยเป็นรายละเอียด เมื่อเลื่อนหน้า กล้องค่อย ๆ เคลื่อนเข้าหาเกมแนะนำหนึ่งเกม ใช้ composition ที่ควบคุมจำนวนวัตถุและตำแหน่งข้อความได้

ฉากนี้ต้องมี storyboard, ภาพนิ่งสำรอง และ asset สำหรับใช้งานจริง ประเมินต้นทุนและประสิทธิภาพจาก prototype ฉากก่อนขยายงาน ไม่ถือว่าภาพหน้าปกเดิมเพียงอย่างเดียวจะให้คุณภาพเทียบงาน 3D ของเว็บอ้างอิง

## 4. โครงสร้างหน้าและเส้นทางผู้ใช้

เส้นทางด้านล่างเป็น path ภายใต้ base ของเว็บ รองรับทั้ง custom domain และ GitHub Pages แบบ repository subpath

| หน้า | หน้าที่และเนื้อหาหลัก |
| --- | --- |
| `/` | แบรนด์, hero, ผลงานเด่น 3–4 เกม, อัปเดตล่าสุด, แนวทางการแปล, สนับสนุน |
| `/mods/` | ค้นหาไทย/อังกฤษ, กรองแนวเกมและแหล่งดาวน์โหลด, เรียงล่าสุด/ชื่อ, รายการโปรด, จำนวนผลลัพธ์ |
| `/mods/<id>/` | ภาพเกม, เครดิต, รุ่นม็อด, ความเข้ากันได้, ดาวน์โหลด, วิธีติดตั้ง/ถอดถอนเท่าที่มีข้อมูล, changelog, แหล่งซื้อ, รายงานปัญหา |
| `/guide/` | คู่มือติดตั้งทั่วไปและคำถามที่พบบ่อย พร้อมลิงก์ไปคำแนะนำเฉพาะเกม |
| `/support/` | แนะนำผู้แปล ช่องทางติดตาม และ QR สนับสนุนที่เจ้าของใช้อยู่ |
| `/404.html` | อธิบายว่าไม่พบหน้า พร้อมค้นหา/กลับคลัง |

เมนู desktop: โลโก้ · คลังม็อด · คู่มือ · สนับสนุน · ค้นหา

เมนูมือถือ: โลโก้ · ค้นหา · เมนู โดยการเปิดเมนูต้องจัดการ focus, Escape และคืน focus เมื่อปิด

ผู้ใช้ใหม่: หน้าแรก → ผลงานเด่น → รายละเอียด → อ่านความเข้ากันได้ → ดาวน์โหลด

ผู้ใช้กลับมา: ค้นหา → รายละเอียด → ดูเวอร์ชันล่าสุด → ดาวน์โหลด

## 6. ระบบ motion และมือถือ

| จุด | Desktop | Mobile / ลดการเคลื่อนไหว |
| --- | --- | --- |
| Hero | ฉาก 3D ตอบสนอง pointer เล็กน้อย เลื่อนกล้องตามช่วงที่กำหนด | mobile ใช้ฉากลดรายละเอียดหรือภาพนิ่ง; reduced motion ใช้ภาพนิ่ง |
| การเลื่อน | เลื่อนแบบ native เป็นฐาน เพิ่ม animation เฉพาะช่วง | เลื่อนตามปกติ ไม่ผูกงานหลักกับ gesture พิเศษ |
| การ์ด | ขยายภาพเล็กน้อยเมื่อ hover/focus | แตะเพื่อเปิดได้ตรง ๆ ข้อมูลสำคัญเห็นตลอด |
| เปิดหน้า | transition สั้นที่ยังทำงานร่วมกับ back/forward | ลดหรือปิดเมื่อผู้ใช้ตั้งค่า reduced motion |
| โหลด asset | เนื้อหาและปุ่มเข้าถึงได้ทันที แสดง poster ระหว่างโหลด | โหลดภาพขนาดเหมาะสมก่อน 3D |

- ฉากต้องหยุด render เมื่ออยู่นอกจอหรือแท็บถูกซ่อน และปล่อย resource เมื่อออกจากหน้า
- มีปุ่มพัก motion และจำการตั้งค่าในอุปกรณ์ รองรับกรณี localStorage ใช้ไม่ได้
- ถ้า WebGL เริ่มไม่ได้หรือเกิด context loss ให้กลับสู่ poster โดยยังใช้เมนูและลิงก์ได้
- ไทยใช้การเคลื่อนไหวเป็นบรรทัดหรือทั้งวลี เพื่อหลีกเลี่ยงการแยกสระ/วรรณยุกต์ผิดตำแหน่ง
- การเปลี่ยนหน้าต้องไม่ทำให้ content หรือ focus หาย หากสคริปต์ motion ล้มเหลว

## 7. สถาปัตยกรรมที่เสนอ

**Astro + TypeScript + content collections + CSS tokens + GSAP/ScrollTrigger + Three.js เฉพาะฉาก hero**

เหตุผลในการเลือก: เนื้อหาเว็บส่วนใหญ่เป็นข้อมูลที่สร้างเป็นหน้า HTML ได้ ตั้งค่า static build และเผยแพร่บน GitHub Pages ต่อได้ ส่วน JavaScript ใช้กับค้นหา รายการโปรด เมนู และ motion ตามจุดที่จำเป็น

นี่เป็นข้อเสนอจากลักษณะงาน ไม่ใช่ข้อสรุปว่าเว็บ Lusion ใช้ stack นี้

โครงสร้างโดยประมาณ:

```text
src/
  content.config.ts          schema และตัวโหลดข้อมูล
  content/mods/<id>.json     ข้อมูลเกมและ release
  pages/index.astro
  pages/mods/index.astro
  pages/mods/[id].astro
  pages/guide.astro
  pages/support.astro
  pages/404.astro
  layouts/BaseLayout.astro
  components/                Header, Card, DownloadPanel, Gallery ฯลฯ
  scripts/                   catalog, favorites, legacy-links, motion
  scenes/hero/               ฉากและการจัดการ WebGL
  styles/                    tokens, global, component styles
public/
  assets/                    รูป โลโก้ poster และ model ที่อนุมัติให้ใช้
scripts/
  migrate-mods.*             ย้ายข้อมูลพร้อมรายงานเทียบเดิม
  validate-content.*         ตรวจ ID, URL, asset และ release
docs/
  content-editing.md         วิธีเพิ่มเกมและอัปเดตม็อด
```

การจัดการเนื้อหารุ่นแรกใช้ไฟล์รายเกมและ review ผ่าน Git ตามงานเดิม หากต้องการหน้าจอแอดมินให้เพิ่ม CMS ในระยะต่อไป โดยคง schema นี้เป็นสัญญาข้อมูล และกำหนดผู้แก้ไข/ขั้นเผยแพร่ก่อนเลือกผู้ให้บริการ

ฟีเจอร์สมาชิก ฐานข้อมูลรายการโปรดข้ามอุปกรณ์ และการรับเงินในเว็บ ยังไม่มีความต้องการจากงานปัจจุบัน จึงไม่ใช่ dependency ของการเปิด V2 ช่องทางสนับสนุนและไฟล์ดาวน์โหลดใช้ของเดิม

## 8. ปรับระบบข้อมูล

ยึด `id` ปัจจุบันเป็น identity ถาวร เก็บชื่อไทย/อังกฤษ เครดิต ปก gallery tags แหล่งซื้อ และ post ต้นทาง แยกข้อมูลการปล่อยม็อดออกเป็น release:

- `version`, `publishedAt`, `changelog`
- `compatibility`: platform, store, build ที่ยืนยันได้ และหมายเหตุ
- `downloads[]`: provider, URL, ขนาดถ้ามี, checksum จริงถ้ามี
- `installSteps`, `uninstallSteps` เฉพาะที่มีแหล่งข้อมูล
- `sourceUrl`, `verifiedAt` และขอบเขตที่ตรวจแล้ว โดยเริ่มว่างหากยังไม่ตรวจ

ส่วนการนำเสนอแยก `featured` และลำดับแนะนำจากข้อมูล release จำนวนม็อดและอัปเดตล่าสุดคำนวณจากข้อมูลจริง

ค่าที่ไม่ทราบให้แสดงว่า “ยังไม่ระบุ” หรือไม่แสดงตามบริบท ไม่เติม build, checksum, ตัวเลขดาวน์โหลด หรือความคืบหน้าขึ้นเอง ข้อมูลทั้ง 32 รายการเป็นข้อมูลตั้งต้นที่ต้องย้ายให้ครบ ยังไม่ได้ตรวจความถูกต้องกับต้นทางใหม่ในงานวางแผนนี้

การค้นหาเก็บใน query string เช่น `/mods/?q=tales&source=nexus&sort=latest` รองรับ refresh, back และการแชร์ผลกรอง สร้าง search index ขนาดเล็กจากข้อมูลตอน build

ทำงานใน branch `codex/redesign-v2` เมื่อเริ่ม implementation เก็บจุดอ้างอิงของเว็บเดิมและผล build เดิมไว้สำหรับ rollback รวมงานผ่าน PR ตามนโยบาย repository

คง URL `?mod=<id>` ด้วยสคริปต์นำไปหน้ารายเกมใหม่หลังตรวจ ID และ base path ส่วน hash เดิม เช่น `#catalog`, `#guide`, `#support`, `#updates`, `#stores` ต้องมี mapping หรือ anchor ปลายทางที่มีความหมาย การกดย้อนกลับต้องไม่วน redirect

ถ้าใช้ GitHub Pages แบบ project site ให้ตั้ง `site`/`base` และสร้างลิงก์ผ่าน helper กลาง ทดสอบทั้ง root และ repository subpath ห้ามอาศัย path `/assets/` แบบตายตัว

ก่อนเปิดใช้ตรวจ manifest, favicon, QR และ metadata ที่อ้างถึงธีมเดิม ปรับ workflow ให้ upload เฉพาะ build output

## 10. เกณฑ์ตรวจรับ

ฟังก์ชันและข้อมูล:

- ย้ายครบ 32 ID และเทียบ download URL, purchase URL, post URL, เครดิต และ release โดยไม่มีข้อมูลตกหล่น
- เข้า URL รายเกมโดยตรงและ refresh ได้ ลิงก์เดิม `?mod=` ใช้ได้ ID ที่ไม่มีอยู่มีทางออกที่ชัดเจน
- ค้นหาไทย/อังกฤษ กรองหลายเงื่อนไข ล้างตัวกรอง ไม่พบผลลัพธ์ และ back/forward ทำงานถูกต้อง
- รายการโปรดเดิมยังอ่านได้บน origin เดิม กรณีเปลี่ยนโดเมนต้องมีแผน export/import เพราะ localStorage ไม่ข้าม origin
- ปุ่มดาวน์โหลดบอก provider และเปิดปลายทางของ release ที่แสดงอย่างถูกต้อง ไม่มีปุ่มจำลอง
- QR สนับสนุนอ่านได้ และคงไฟล์ต้นฉบับ/บันทึกที่มา
- HTML หลักและลิงก์รายเกมใช้ได้แม้ JavaScript ถูกปิด การค้นหาแบบโต้ตอบแจ้งข้อจำกัดอย่างชัดเจน

ภาพและการเข้าถึง:

- ตรวจความกว้าง 360, 390, 768, 1280 และ 1440px รวมทั้ง browser zoom 200%
- ไม่ตัดสระ/วรรณยุกต์ ไม่มี horizontal overflow และไม่ซ่อน CTA ไว้เฉพาะ hover
- ใช้ semantic links/buttons, focus ที่เห็นชัด, label สำหรับค้นหา และสถานะผลลัพธ์ที่อ่านได้ด้วย screen reader
- ตอบสนอง reduced motion, ปุ่มพัก, WebGL ไม่รองรับ และ context loss
- ตรวจ browser console และ asset ที่โหลดล้มเหลวในเส้นทางหลัก

เป้าหมายประสิทธิภาพตั้งต้น (เป็นเกณฑ์ออกแบบ ยังไม่ได้วัด):

- ให้ข้อความ hero และ CTA ปรากฏก่อนโหลดฉากสามมิติ
- JavaScript จำเป็นต่อเส้นทางค้นหา/รายละเอียดไม่เกินประมาณ 120 KB gzip โดยโหลด Three.js และ asset ฉากแยกจากเส้นทางนี้
- poster บนมือถือเริ่มที่ไม่เกินประมาณ 250 KB พร้อมขนาดภาพ responsive
- ตั้งเป้า LCP ≤ 2.5 วินาที, INP ≤ 200 ms, CLS ≤ 0.1 ที่ percentile 75 เมื่อมี field data เพียงพอ ก่อนเปิดใช้ใช้ lab test เป็นสัญญาณเบื้องต้นและระบุเครื่อง/เครือข่ายที่ทดสอบ
- ตั้งเป้าฉากลื่นใกล้ 60fps บนเครื่องทดสอบ desktop และอย่างน้อย 30fps บนมือถือระดับกลางที่ระบุรุ่น หากไม่ผ่านลดรายละเอียดหรือใช้ poster

## 11. จุดเริ่มงานรอบถัดไป

เริ่มจากแบบหน้าแรกและหน้ารายเกมที่ใช้ข้อมูลจริงหนึ่งเกม พร้อม prototype ฉาก hero เพื่อยืนยันภาพรวมและข้อจำกัดการแสดงผล จากนั้นจึงขยาย component และย้ายข้อมูลทั้งคลังตาม schema ที่ผ่านการทดลองแล้ว
